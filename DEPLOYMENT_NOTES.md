# Deployment Notes — Local Docker (working log)

> Scratch reference, not a submission artifact. Kept alongside `DEPLOYMENT.md` so every issue
> hit while deploying to local Docker — and exactly how it was resolved — is recorded while
> it's fresh, before being distilled into `DEPLOYMENT.md`'s own "Notes / trade-offs" section.
> Environment: Windows 11, Docker Desktop 29.5.3, WSL2 backend, Linux containers.

## Issues log

| # | Issue | Cause | Resolution | Status |
|---|---|---|---|---|
| 1 | Healthcheck likely always reports `unhealthy` | `docker-compose.yml`'s healthcheck runs `curl -f http://localhost:8080/api/tasks` **inside** the container, but the base `mcr.microsoft.com/dotnet/aspnet:8.0` runtime image does not include `curl`. | Added a `RUN apt-get update && apt-get install -y --no-install-recommends curl && rm -rf /var/lib/apt/lists/*` step to the runtime stage in `Dockerfile`. | Fixed & verified |
| 2 | `docker compose build` fails during `dotnet publish` with `NuGet.Packaging.Core.PackagingException: Unable to find fallback package folder 'C:\Program Files (x86)\Microsoft Visual Studio\Shared\NuGetPackages'` | No `.dockerignore` existed, so `COPY src/ src/` in the Dockerfile copied every project's local `obj/` folder (generated by `dotnet build`/`dotnet test` already run on Windows for this repo) into the Linux build context — including `obj/*.csproj.nuget.g.props`, which embeds the **Windows host's** NuGet fallback-folder path. `dotnet publish --no-restore` picked up that stale, Windows-specific `obj/project.assets.json` instead of a container-native one, and failed resolving a path that only exists on the Windows host, not inside the Linux build stage. | Added a `.dockerignore` at the repo root excluding `bin/`, `obj/`, `.git/`, `.vs/`, `.vscode/`, `.harness/output/`, `coverage/` so the Docker build context — and the `COPY src/ src/` step specifically — only ever sees source files, never host-machine build artifacts. This is the standard fix for ".NET repo built locally on Windows, then Dockerized" and is missing from most starter Dockerfiles unless added deliberately. | Fixed & verified |
| 3 (informational, not an error) | Container log line on startup: `warn: Microsoft.AspNetCore.Hosting.Diagnostics[15] Overriding HTTP_PORTS '8080' and HTTPS_PORTS ''. Binding to values defined by URLS instead 'http://+:8080'.` | The `dotnet/aspnet:8.0` base image sets a default `HTTP_PORTS=8080` env var; the `Dockerfile` also sets `ASPNETCORE_URLS=http://+:8080` explicitly. ASP.NET Core's startup logs a warning whenever both are present, even though the outcome (`URLS` wins) is exactly what's intended. | None needed — this is expected, benign, and does not affect behavior. Documented here only so it isn't mistaken for a real problem when reviewing logs. | Not an issue |

## Files changed to get a clean deployment

- `Dockerfile` — added `curl` install to the runtime stage (issue #1)
- `.dockerignore` — new file (issue #2)
- `docker-compose.yml` — unchanged; the existing healthcheck definition was correct once `curl` existed to run it

## Summary

Two real defects found and fixed in the pre-existing `Dockerfile`/`docker-compose.yml`
scaffold (neither was introduced by this session — both predate the harness's feature work
and would have hit anyone deploying this repo to Docker for the first time). Container now
builds, starts, reports `healthy`, and the full SLA-breach-alerting pipeline (sweep →
notify → escalate) verified working end-to-end against the containerized app.
